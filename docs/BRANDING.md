# ORCHORDS AI Branding and Documentation Style

This repository follows the public-documentation presentation pattern established in [`ORCHORDS/docs`](https://github.com/ORCHORDS/docs) while keeping product-specific engineering material local to ORCHORDS AI.

## Product name

Use **ORCHORDS AI** in public prose, headings, screenshots, issue-form copy, and documentation.

Preserve technical identifiers when changing them would break compatibility or misrepresent a third party. Examples include:

- repository name `OrchordsAI`;
- Android package/application IDs;
- artifact patterns such as `OrchordsAI-<version>-<abi>.apk`;
- protocol, vendor, dependency, and third-party project names;
- license and attribution text.

## Repository-level documents

Root public documents may use the official ORCHORDS banner maintained by [`ORCHORDS/docs`](https://github.com/ORCHORDS/docs) and should end with the brand line:

**ORCHORDS — BUILD DIFFERENT.**

## Controlled product documents

Product engineering documents under `docs/` use the same controlled-document metadata fields as ORCHORDS public documentation:

- `title`
- `owner`
- `status`
- `classification`
- `last-reviewed`
- `review-cycle`
- `next-review`

Dates describe documentation review state; they do not claim that a product control, certification, audit, or external assurance exists.

## Module documentation

Module and package READMEs use light branding: an `ORCHORDS AI` title and, where useful, the ORCHORDS brand line. Do not insert large banners into source-tree documentation where they add noise.

## Legal and third-party boundary

Branding must never replace, obscure, or rewrite required third-party names, license notices, copyright notices, attribution, protocol names, or compatibility identifiers.
